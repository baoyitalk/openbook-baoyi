
好问题，这是很多人的困惑点。

## JS 单线程指的是"执行代码"单线程

但发请求、定时器这些 I/O 操作不是 JS 引擎干的，是浏览器/Node 的其他线程干的。

```
┌─────────────────────────────────────────┐
│            浏览器 / Node                 │
│  ┌─────────────┐  ┌─────────────────┐   │
│  │  JS 主线程   │  │  其他线程        │   │
│  │  (单线程)    │  │  - 网络线程      │   │
│  │             │  │  - 定时器线程    │   │
│  │  执行代码    │  │  - 文件 I/O     │   │
│  └─────────────┘  └─────────────────┘   │
└─────────────────────────────────────────┘
```

## 实际流程

```javascript
setTimeout(cb1, 1000)  // JS: "浏览器，帮我计时1秒"，然后继续往下
setTimeout(cb2, 1000)  // JS: "浏览器，再帮我计时1秒"，继续往下
setTimeout(cb3, 1000)  // JS: "浏览器，再来一个"，继续往下

// 三个定时器同时在跑（浏览器线程干的）
// 1秒后，三个回调几乎同时被丢进任务队列
// JS 主线程依次执行 cb1, cb2, cb3
```

## 总结

- 单线程：执行 JS 代码
- 多线程：I/O 操作（网络请求、定时器、文件读写）

所以"同时发三个请求"没问题，只是"同时执行三个回调"不行，得排队一个来。



setTimeout(cb3, 1000)  // 最后这行代码 执行肯定慢于前两个 但是是0.001级别 感知不出来 所以
也勉强说是并行了

你说的没错，确实有时间差，但这个差距可以忽略不计。

```javascript
const t = Date.now()

setTimeout(() => console.log('cb1', Date.now() - t), 1000)
setTimeout(() => console.log('cb2', Date.now() - t), 1000)
setTimeout(() => console.log('cb3', Date.now() - t), 1000)

// 输出大概：
// cb1 1001
// cb2 1001
// cb3 1001
```

## 为什么差距可以忽略

```javascript
setTimeout(cb1, 1000)  // 执行这行代码 ≈ 0.001ms
setTimeout(cb2, 1000)  // 执行这行代码 ≈ 0.001ms
setTimeout(cb3, 1000)  // 执行这行代码 ≈ 0.001ms
```

三行代码执行完总共可能 0.01ms，而定时器是 1000ms。

## 极端情况：你说的 0.01ms

```javascript
setTimeout(cb1, 0)
setTimeout(cb2, 0)
setTimeout(cb3, 0)
```

这时候确实有先后顺序，cb1 先进队列，cb3 最后。但浏览器 setTimeout 最小延迟是 4ms 左右，所以实际上它们几乎同时到期，按注册顺序依次执行。

## 真正有影响的场景

```javascript
setTimeout(cb1, 1000)
// 这里有个耗时操作，比如循环 1 亿次，花了 500ms
for (let i = 0; i < 100000000; i++) {}
setTimeout(cb2, 1000)

// cb1 在 1000ms 后触发
// cb2 在 1500ms 后触发（因为注册晚了 500ms）
```

正常写代码不会这样，所以实际开发中可以认为"同时发出"。
