# 基于第一性原理：拆解「为何不用全局变量，非要用闭包」
你的疑问直击核心——**技术上，用全局变量确实能实现缓存/防抖/节流等逻辑，但从「工程化」和「JS底层设计」的元规则出发，全局变量存在「无法解决的致命缺陷」，而闭包是JS中「优雅解决这些缺陷」的唯一方案**。

我们先锚定JS的核心元前提，再用「防抖」这个最典型的场景做对比，让差异一目了然。

## 前置：锚定2个不可动摇的元前提（所有推导的根基）
1. **元前提1**：JS的「全局作用域」是**共享作用域**——所有脚本、函数、组件都能访问/修改全局变量，无任何隔离性；
2. **元前提2**：JS的「函数作用域/闭包作用域」是**私有作用域**——只有闭包内部的函数能访问该作用域的变量，外部无法触及；
3. **元前提3**：复杂应用的核心需求是「状态隔离」——多个独立的防抖/缓存/节流函数，需要各自保留独立的状态（如定时器ID、缓存表），互不干扰。

---

## 一、先验证：全局变量确实能实现，但问题致命
我们用「防抖」为例，先写一个全局变量版的实现，再拆解它的问题：

### 1. 全局变量版防抖（技术上可行）
```javascript
// 全局变量：保存定时器ID
let globalTimer = null;

// 全局版防抖函数
function debounceWithGlobal(fn, delay) {
  return function(...args) {
    clearTimeout(globalTimer); // 访问全局变量
    globalTimer = setTimeout(() => fn(...args), delay); // 修改全局变量
  };
}

// 测试1：按钮1的防抖点击
const handleClick1 = () => console.log('按钮1点击');
const debounceClick1 = debounceWithGlobal(handleClick1, 1000);

// 测试2：按钮2的防抖点击
const handleClick2 = () => console.log('按钮2点击');
const debounceClick2 = debounceWithGlobal(handleClick2, 1000);
```

### 2. 全局变量版的致命问题（从元前提推导）
#### 问题1：状态冲突（违反元前提3）
当你快速点击「按钮1」和「按钮2」时：
- 点击按钮1 → `globalTimer` 被设置为按钮1的定时器ID；
- 紧接着点击按钮2 → `clearTimeout(globalTimer)` 会清除按钮1的定时器，同时将`globalTimer`覆盖为按钮2的ID；
- 最终结果：按钮1的防抖逻辑完全失效，只有按钮2的逻辑执行——**多个防抖函数共享一个全局状态，互相干扰**。

#### 问题2：全局污染（违反元前提1）
- `globalTimer` 暴露在全局作用域中，任何代码都能随意修改：比如其他脚本不小心执行 `globalTimer = null`，会直接导致所有防抖函数失效；
- 复杂项目中，全局变量会越来越多（`globalCache`、`globalLastTime`...），命名冲突、误修改的概率呈指数级上升。

#### 问题3：内存泄漏（违反元前提2）
- 全局变量不会被JS的垃圾回收机制回收（除非手动删除），即使防抖函数不再使用，`globalTimer` 依然占用内存；
- 闭包的变量仅在「防抖函数被引用」时存在，当防抖函数被销毁（如组件卸载），闭包作用域会被回收，无内存泄漏风险。

#### 问题4：维护灾难
- 全局变量的状态归属不明确：当防抖逻辑出问题时，你无法快速定位「哪个函数修改了globalTimer」；
- 闭包的状态是「函数级私有」，问题定位范围被严格限定在防抖函数内部。

## 二、闭包版防抖：完美解决所有问题（从元前提推导）
```javascript
function debounceWithClosure(fn, delay) {
  let closureTimer = null; // 闭包私有变量：每个防抖函数独立拥有
  return function(...args) {
    clearTimeout(closureTimer); // 访问闭包私有变量
    closureTimer = setTimeout(() => fn(...args), delay); // 修改闭包私有变量
  };
}

// 测试1：按钮1的防抖（独立闭包状态）
const debounceClick1 = debounceWithClosure(() => console.log('按钮1点击'), 1000);

// 测试2：按钮2的防抖（独立闭包状态）
const debounceClick2 = debounceWithClosure(() => console.log('按钮2点击'), 1000);
```

### 闭包的核心优势（对应解决全局变量的问题）
#### 优势1：状态完全隔离（符合元前提3）
- 每次调用 `debounceWithClosure`，都会创建一个**独立的闭包作用域**，里面的`closureTimer`只属于当前防抖函数；
- 按钮1的`closureTimer`和按钮2的`closureTimer`互不干扰，点击按钮1不会影响按钮2的防抖逻辑。

#### 优势2：无全局污染（符合元前提2）
- `closureTimer` 存在于闭包私有作用域中，外部代码无法访问/修改，彻底避免误操作；
- 即使项目中有100个防抖函数，也不会新增任何全局变量。

#### 优势3：内存可控
- 当某个防抖函数不再使用（如组件卸载，`debounceClick1 = null`），对应的闭包作用域会被垃圾回收，`closureTimer` 也会被清理；
- 相比全局变量的“永久占用内存”，闭包的内存占用是「按需分配、按需释放」。

#### 优势4：维护性极强
- 状态的归属明确：每个防抖函数的状态都封装在自身的闭包中，问题定位范围极小；
- 符合「最小权限原则」：变量只在需要它的作用域中存在，不暴露多余的状态。

## 三、核心结论（面试金句，直接背）
1. **技术可行性**：用全局变量确实能实现缓存/防抖/节流等逻辑，但会引入「状态冲突、全局污染、内存泄漏」等致命问题，完全不适合工程化开发；
2. **闭包的核心价值**：在「非全局作用域」中实现「私有、隔离、持久化的状态」——这是JS中唯一能同时满足「状态持久化（跨调用保存）」和「状态隔离（互不干扰）」的方案；
3. **底层逻辑**：闭包的本质是「函数作用域的持久化」，它既解决了全局变量的“共享污染”问题，又解决了普通函数作用域“变量随函数执行销毁”的问题，是平衡「状态持久化」和「状态隔离」的最优解。

简单说：**全局变量是“裸奔的状态”，闭包是“封装好的私有状态”** ——前者能跑，但无法在复杂应用中稳定运行；后者才是符合工程化、可维护性的解决方案。
