# 实战高频面试题（费曼一问一答版）

> 说明：本稿只保留普通一问一答，不做追问链。
> 每题统一费曼四段：学习理解 / 大白讲解 / 漏洞卡点 / 压缩总结。

---

## 一、项目与跨端

### Q1：你最近项目最大的难点是什么？
**A（费曼四段）**
1. 学习理解：真正的难点通常不是"某个功能不会写"，而是多个约束同时存在。比如多端能力不一致、历史代码耦合重、线上稳定性要求高、业务节奏又快，这些会互相拉扯。
2. 大白讲解：打个比方，难点就像你要一边开车一边换轮胎——不能停下来，还必须保证车还能跑。在实际项目里，这意味着你不能直接删掉旧代码重来一遍，因为线上业务不能停；也不能无限期拖，因为业务迭代不等人。所以真正的"难"不是技术不会，而是在"改动要安全、交付要快、质量要保证"这几个目标同时拉扯的情况下，找出一条能走通的路。我的做法是先把问题分层，哪些是高耦合必须小心动的，哪些是可以隔离试验的，再按风险高低排序拆步骤，每步都有可验证的结果和回滚方案。
3. 漏洞卡点：只说"很难"但讲不出拆解方法；或者只讲动作，不讲为什么选这条路。
4. 压缩总结：难点是多约束冲突，解法是分层拆解+低风险推进+指标验证。

### Q2：为什么你选择渐进迁移，而不是一次性重构？
**A（费曼四段）**
1. 学习理解：渐进迁移本质是风险管理策略。一次性重构改动面太大，线上风险集中，失败成本高。
2. 大白讲解：想象你要改造一栋在住的楼，一次性推倒重建代价极高，而且住户没地方住。渐进迁移就是"先改一个房间，住户体验没问题，再改下一个"。在代码迁移里，我会先选一个流量小、逻辑简单、回滚方便的页面或模块做试点，跑一段时间，指标没问题、没出线上事故，再把经验复制到下一个模块。每一步背后都有开关，出了问题直接关掉，不会牵连整体。这样整个过程始终可控，失败代价小。如果一次性重构，改动面太大，测试覆盖不全，上线之后一旦出问题很可能不知道是哪里坏的，而且回滚代价极高。
3. 漏洞卡点：只会说"分批做"，但说不清按什么标准分批。
4. 压缩总结：渐进迁移的核心价值是可控交付和可回滚。

### Q3：为什么有跨端框架还要做 JSBridge 适配层？
**A（费曼四段）**
1. 学习理解：适配层不是重造框架，而是统一通信协议，降低业务接入复杂度。
2. 大白讲解：现实是这样的：同一个 `扫一扫` 功能，在 iOS 上调原生接口的方式，和在 Android 上不一样，甚至不同 App 版本之间的参数也可能有差异。如果业务层的每个开发都要自己判断端、自己做兼容，那是重复劳动，而且谁写谁挖坑。适配层做的事情，就是把这些差异收进一个统一的 `invoke` 接口，业务层不管在哪个端，只调用同一套 API，剩下的路由和兼容逻辑由适配层来做。好处是双向的：业务接入成本大幅下降，出了问题也只用查一个地方，而不是到处翻业务代码。这个思路本质上是"接口收口"，和后端设计 Gateway 是同一个道理。
3. 漏洞卡点：边界不清，容易被问成"你是不是重复造轮子"。
4. 压缩总结：做的是协议统一，不是渲染重造。

### Q4：你怎么做首屏优化？
**A（费曼四段）**
1. 学习理解：首屏优化是链路问题，不是单点问题。要同时看资源加载、接口请求、渲染耗时。
2. 大白讲解：首先我不会一上来就开始改代码，而是先用工具（Lighthouse、Performance 面板、线上 RUM 数据）定位到底是哪个环节慢。是 JS 包太大下载慢？还是接口串行等太久？还是渲染阶段重排次数太多？定位完了再针对性优化：包太大的话做代码分割，把首屏不需要的代码懒加载进来；接口慢的话看能不能并行发请求，或者服务端聚合成一个；渲染卡的话减少首屏 DOM 数量、把不必要的同步计算移出渲染路径。最后必须用数据说话——LCP（最大内容绘制）和 FCP（首次内容绘制）这两个指标，优化前后都要记录，没有数字提升就不算做完。
3. 漏洞卡点：只报优化动作，没有指标结果。
4. 压缩总结：先测量再优化，最终用线上指标说话。

### Q5：跨域在项目里你怎么处理？
**A（费曼四段）**
1. 学习理解：跨域是浏览器同源策略带来的限制，核心是来源控制和预检配置。
2. 大白讲解：跨域问题在开发和生产两个场景是完全不同的处理方式。开发阶段，前端和后端通常端口不同，我会在 Vite 或 webpack 的 devServer 里配一个代理，把 `/api` 的请求转发到后端服务，浏览器以为是同源请求，联调就顺畅了。生产环境就不一样了，代理不能用，要靠服务端真实配置 CORS 响应头——告诉浏览器哪些来源被允许，哪些 Header 被允许。这里有一个容易漏的细节：带凭证的请求（比如带 Cookie）要额外设置 `withCredentials: true`，同时服务端的 `Access-Control-Allow-Origin` 不能写 `*` 必须写明确的域名，否则浏览器会直接拦截。另外 `OPTIONS` 预检请求一定要处理好，漏了这个会导致 POST/PUT 等复杂请求全部失败，这个坑踩过一次就不会忘。
3. 漏洞卡点：漏配 OPTIONS 预检或凭证配置不一致。
4. 压缩总结：开发走代理，生产走 CORS，预检必须正确。

### Q6：你怎么证明项目产出价值？
**A（费曼四段）**
1. 学习理解：价值不是"我觉得更好了"，而是可量化变化。
2. 大白讲解：面试官问这个，其实是在考你有没有结果意识。光说"做了 XX 优化"是不够的，因为每个人都会这么说。有说服力的回答是："我们首屏 LCP 从 3.8 秒降到了 2.1 秒，降幅 45%；同期线上 JS 报错率下降了 30%；发版周期从两周缩短到一周。"这些数字是怎么来的？要有基线、有优化后的对照、最好有时间范围。如果项目当时没有留数据，那应该坦诚说"那时候没有完善的监控体系，这是我现在的遗憾之一，后来我会确保做事情前先建指标"——这样反而加分，说明你有复盘意识。
3. 漏洞卡点：只讲过程，不讲结果。
4. 压缩总结：产出要量化，最好有基线和对照。

## 二、React 核心与 Hooks

### Q7：React 你用得最深的点是什么？
**A（费曼四段）**
1. 学习理解：深度不在 API 数量，而在于能否控制渲染成本和更新边界。
2. 大白讲解：大多数人用 React 是"能跑就行"，但深度用的人会关注"这次更新有没有触发不必要的渲染"。我的习惯是，先用 React DevTools Profiler 火焰图找出渲染热点——哪些组件在状态没变的情况下频繁重渲染。找到之后再做最小必要的优化：组件粒度拆细，用 `React.memo` 包住稳定组件，`useMemo` 缓存计算量大的值，`useCallback` 稳定传递给子组件的函数引用。比如一个长列表页面，父组件状态变了，但列表项的数据根本没变，这时候每个列表项都重渲染就是浪费。不是什么都加 memo，而是先量、再治，过度优化有时候反而让代码变复杂、可读性更差。
3. 漏洞卡点：过度优化导致代码复杂，收益反而不明显。
4. 压缩总结：React 深度=定位瓶颈+治理更新边界。

### Q8：React Diff 核心原理怎么讲？
**A（费曼四段）**
1. 学习理解：Diff 目标是减少真实 DOM 操作，核心规则是同层比较、类型变更替换、列表靠 key 复用。
2. 大白讲解：Diff 算法的出发点是——操作真实 DOM 很贵，能不动就不动。React 的策略是这样的：首先只在同一层级的节点之间比较，不跨层；其次如果节点类型变了（比如 `div` 变成 `span`），直接替换整棵子树，不硬凑；最重要的是列表的比较，靠的是 `key` 来判断"这个节点是旧列表里的哪一个"。如果 `key` 稳定且唯一，React 可以高效复用旧节点、只改变位置；如果你用 index 当 `key`，列表一旦有插入或删除，所有节点的 key 都会位移，React 以为全部换了，就会全量重渲染，甚至出现输入框内容乱跳的 bug——这是面试里最常考的陷阱之一。
3. 漏洞卡点：用 index 当 key 导致状态错位。
4. 压缩总结：Diff 的重点是"尽量复用，减少无效变更"。

### Q9：为什么引入 Fiber？
**A（费曼四段）**
1. 学习理解：Fiber 是调度模型升级，解决大任务不可中断导致主线程卡顿的问题。
2. 大白讲解：在 Fiber 之前，React 的更新是同步递归的——一旦开始更新组件树就停不下来，如果组件树很深，这个过程可能要几十甚至上百毫秒。这期间浏览器没办法响应用户操作，页面就卡住了，体验很差。Fiber 的核心改变是：把更新任务拆成一个个小片段，每执行一个片段就检查一下"有没有更高优先级的事情要做"，比如用户点击或者动画帧。有的话，先放下当前工作，去处理高优先级的，再回来接着做。这就是"可中断调度"。同时 Fiber 引入了优先级概念，用户输入比后台数据刷新优先级高，React 能根据优先级决定什么先执行。要注意的是，Fiber 是调度层的改造，Diff 算法本身没有变，这两个概念容易被混淆。
3. 漏洞卡点：把 Fiber 说成 Diff 替代算法。
4. 压缩总结：Fiber 管调度节奏，Diff 管变更范围。

### Q10：useEffect 常见坑怎么回答？
**A（费曼四段）**
1. 学习理解：`useEffect` 的难点是依赖管理和副作用清理。
2. 大白讲解：`useEffect` 是前端状态管理里坑最多的地方，主要有三类问题。第一是依赖写漏：你在 effect 里用了某个变量，但没放进依赖数组，导致 effect 内部读到的是旧的闭包值，行为和预期不一致——这种 bug 很隐蔽，测试很难稳定复现。第二是依赖写多：每次渲染都产生新的对象或函数引用，导致 effect 无限循环执行，控制台疯狂打日志，严重的会把接口打爆。第三是没做 cleanup：开了一个订阅、加了一个事件监听，组件卸载时没清掉，内存就一直堆积，或者组件卸载后还往 state 里写值，触发 React 的警告。正确做法是：依赖用 ESLint 插件辅助检查、对象用 `useMemo` 稳定引用、副作用必须在 return 里清理，比如取消请求、移除监听。
3. 漏洞卡点：闭包旧值和依赖遗漏最容易翻车。
4. 压缩总结：依赖完整、清理彻底、时序清楚。

### Q11：props、context、ref 怎么区分？
**A（费曼四段）**
1. 学习理解：props 是显式传值，context 是跨层共享，ref 是不触发渲染的可变引用或 DOM 访问。
2. 大白讲解：这三个工具各有自己的适用场景，不能随意互换。`props` 是最基础的数据流动方式，父组件明确把什么给子组件，清晰可追踪，是首选；但如果层级很深，每层都要透传同一个值，写起来很累，这时候 `context` 就有价值了——比如主题色、用户信息这类全局稳定的东西，适合放 context，不需要每层手动传。但 context 有个代价：只要 context 值变了，所有消费它的组件都会重渲染，所以千万不要把高频变化的状态放进去，否则性能会很差。`ref` 是另一类工具，它的核心特性是"改变了不触发渲染"，适合存一些跟渲染无关的东西，比如计时器 ID、上一次的值、或者直接操作 DOM。三者的选择口诀：优先 props，跨层稳定共享才 context，不参与渲染才 ref。
3. 漏洞卡点：把高频状态塞进 context，引发全局重渲染。
4. 压缩总结：按职责选工具，不要为了省事滥用。

### Q12：为什么事件循环在前端面试高频？
**A（费曼四段）**
1. 学习理解：很多异步 bug 本质是时序 bug，事件循环决定执行顺序。
2. 大白讲解：JavaScript 是单线程的，但它可以"看起来并发"，靠的就是事件循环机制。执行顺序是这样的：先把同步代码全部跑完，然后清空微任务队列（Promise 的 `.then`、`queueMicrotask` 等），再从宏任务队列里拿一个任务（`setTimeout`、`setInterval`、I/O 回调等）执行，执行完再清微任务，如此循环。常见的面试题就是考你能不能准确预判一段混合了 `setTimeout`、`Promise`、同步代码的程序的输出顺序。实际开发中这很重要——比如你在 `setState` 之后立刻读取 DOM 高度，拿到的可能还是旧的，因为渲染是下一个宏任务；又比如 `setTimeout(fn, 0)` 不是"立刻执行"，而是"下一个宏任务再执行"，前面所有微任务都要先走完。搞清楚这个，异步 bug 的定位效率能提高一大截。
3. 漏洞卡点：把 setTimeout 当"立刻执行"。
4. 压缩总结：顺序不清，异步必乱。

## 三、工程化与性能优化

### Q13：Vite 和 webpack 怎么选？
**A（费曼四段）**
1. 学习理解：选型看项目约束，不看热度。Vite 开发快，webpack 兼容复杂历史生态更稳。
2. 大白讲解：Vite 之所以开发体验好，是因为它利用浏览器原生 ESM，按需编译，不需要提前把整个项目打包，所以启动快、热更新快。新项目从零开始，技术栈比较现代，优先选 Vite 是合理的。但如果是已经运行了三五年的老项目，用了大量 webpack 生态的插件（比如某些特殊的 loader、webpack 特有的 require.context 等），贸然切换 Vite 意味着要评估所有插件有没有等价替代，迁移成本可能很高。我的判断标准是：新项目 Vite，老项目先做一次插件链评估，如果迁移成本低就切，成本高就保持 webpack 继续优化，不为了赶时髦强切。面试时说"Vite 快所以选 Vite"是不够的，要说出选型背后的取舍逻辑。
3. 漏洞卡点：只讲"快"，不讲迁移风险。
4. 压缩总结：先看场景，再选工具。

### Q14：webpack 优化你一般怎么做？
**A（费曼四段）**
1. 学习理解：优化分三块：构建提速、包体减重、缓存命中。
2. 大白讲解：webpack 优化不是一个动作，而是三个维度同时推进。第一，构建提速：开启 `thread-loader` 或 `babel-loader` 的并行编译，对不变的依赖（比如 node_modules）用 `cache-loader` 或者 webpack5 自带的持久化缓存，这两个组合起来构建时间能压缩 30%~50%。第二，包体减重：用 `webpack-bundle-analyzer` 分析包的组成，找出被重复引入的大依赖，然后通过 `SplitChunksPlugin` 抽公共包；业务代码按路由做 code split，首屏只加载必要的 JS；Tree Shaking 确保有效，前提是所有模块都用 ESM 写法。第三，缓存命中：output 里用 `contenthash` 命名文件，内容不变哈希就不变，用户浏览器能复用缓存，减少不必要的网络请求。最后一定要用数字验证：构建时长、主包大小、缓存命中率，优化前后都要记录。
3. 漏洞卡点：会说术语但拿不出前后对比。
4. 压缩总结：提速、减包、命中率一起做。

### Q15：SSR 改造要讲哪些关键点？
**A（费曼四段）**
1. 学习理解：SSR 用服务端先产首屏，提升可见速度和 SEO，但增加同构复杂度和服务端压力。
2. 大白讲解：SSR 的核心价值是：用户发请求，服务端直接返回一个带内容的 HTML，浏览器立刻就能看到页面，而不是等 JS 下载完再执行、再发接口、再渲染。但它带来的复杂度也是真实的，有几个关键点要说清楚：一是数据预取，服务端要在渲染组件之前把数据准备好，而且这份数据还要"注水"（hydrate）到客户端，客户端接管后不能重复请求；二是同构代码，同一份代码既跑在服务端又跑在浏览器，你不能用 `window`、`document` 这类只有浏览器才有的 API，必须做环境判断；三是缓存策略，热门页面的 SSR 结果如果每次都现算，服务端压力会很大，必须有页面级或片段级缓存；四是降级保底，SSR 服务挂了要能自动降级成 CSR，保证用户还能用，不能单点挂整站。
3. 漏洞卡点：只讲收益不讲代价。
4. 压缩总结：SSR 提升首屏，代价是工程复杂度上升。

### Q16：性能治理怎么做长期有效？
**A（费曼四段）**
1. 学习理解：性能会自然回退，必须流程化治理。
2. 大白讲解：做过性能优化的人都知道一件事——优化后几个版本，性能就慢慢回退了。原因很简单：新功能加进来、依赖包升级、没人注意，慢慢地首屏又变慢了。所以性能治理不是一次冲刺，而是要把它变成流程的一部分。具体来说：把关键性能指标（LCP、FCP、包大小上限、JS 报错率）写进 CI 流程，每次发版都自动跑一遍，超过阈值就发告警、甚至 Block 发布；线上搭 RUM（真实用户监控），持续采集数据，一旦指标异动能快速定位是哪次发版引入的；团队内部定期（比如每月）做一次性能复盘，看趋势而不只看单点。这样性能才能真正守住，而不是靠某个人的自觉。
3. 漏洞卡点：只做一次优化，不做持续治理。
4. 压缩总结：性能靠机制守住，不靠一次冲刺。

### Q17：怎么把构建优化和线上体验打通？
**A（费曼四段）**
1. 学习理解：构建指标是过程，RUM 指标是结果。
2. 大白讲解：很多人做了 webpack 优化之后，汇报的是"包从 2MB 降到了 1.2MB"，但面试官追问"线上用户体验有什么变化"就答不上来了。这两者之间是有断层的：包变小，可能只是构建产物好看，但如果大部分用户命中了缓存，其实体验没变；反过来，包只降了一点，但如果是首屏关键路径上的包，那 LCP 可能会有明显改善。打通的方式是：构建侧的数据（包大小、chunk 数量、构建时间）和线上侧的数据（LCP、FCP、TTFB、用户交互延迟、JS 错误率）要一起看，每次优化完都要拿两侧数据做对照，形成因果链。只靠包大小这一个指标做决策，太片面了。
3. 漏洞卡点：拿 bundle 大小当唯一胜负标准。
4. 压缩总结：过程指标 + 结果指标双闭环。

### Q18：技术方案选型怎么体现工程思维？
**A（费曼四段）**
1. 学习理解：核心是收益、风险、成本、回滚能力平衡。
2. 大白讲解：有工程思维的选型和没有的，差别就在于"会不会提问题"。没有工程思维的人选方案，看的是技术是不是最新、文档写得好不好、GitHub Star 多不多。有工程思维的人会问：这个方案我们团队能维护吗？如果出了问题能回滚吗？灰度上线的方案是什么？引入这个依赖的隐性成本（学习成本、未来升级成本）是多少？跟现有架构冲不冲突？面试时可以这样组织回答：先说自己评估了哪些维度，再说每个候选方案在这些维度上各是什么情况，最后说选了哪个、权衡点在哪里。这比直接说"选了 X 因为它比较流行"要扎实得多。
3. 漏洞卡点：只谈技术理想，不谈落地约束。
4. 压缩总结：最优方案是可交付且可持续的方案。

## 四、手写题与算法题

### Q19：Promise.all 和 allSettled 区别？
**A（费曼四段）**
1. 学习理解：all 强一致成功语义，allSettled 容错汇总语义。
2. 大白讲解：`Promise.all` 的行为是"全赢才赢，一输立刻输"——只要其中一个 Promise reject，整个 all 立刻 reject，其他还在跑的 Promise 结果直接忽略。适合场景是：多个请求都必须成功，任何一个失败都没意义，比如一个页面同时需要用户信息和权限数据，缺一个都不能渲染。`allSettled` 则是"不管成败，等所有人都结束"——每个 Promise 不管 resolve 还是 reject，最终都会把结果（包括状态和值/原因）汇总成数组返回给你。适合场景是：批量操作，比如批量上传 10 个文件，不管每个成不成，最后要知道哪些成了哪些失败了，然后统一展示结果。面试里容易搞反：用了 all 但期望容错，结果第一个失败就整个崩了。
3. 漏洞卡点：搞反短路行为。
4. 压缩总结：严成功 all，容错汇总 allSettled。

### Q20：防抖和节流怎么区分？
**A（费曼四段）**
1. 学习理解：防抖保留最后一次，节流控制频率。
2. 大白讲解：两个都是"限制函数执行频率"的手段，但逻辑完全不同。防抖（debounce）的意思是：只要你还在触发，我就一直等你停下来，停了之后隔一段时间才执行。就像电梯关门——只要还有人按，就一直等，最后一个人走了才关。典型场景是搜索框输入联想，用户打字过程中不发请求，停了 300ms 才发，避免每打一个字就打一次接口。节流（throttle）的意思是：不管你触发多频繁，我每隔固定时间最多执行一次，不会因为你停下来就马上执行。就像水龙头——不管水压多大，阀门限制了流量。典型场景是滚动监听、鼠标移动，每隔 100ms 采样一次就够了，不需要跟着每个像素变化都处理。
3. 漏洞卡点：场景用反。
4. 压缩总结：输入防抖，滚动节流。

### Q21：LRU 缓存你怎么讲？
**A（费曼四段）**
1. 学习理解：LRU 是有限容量下保留"最近最常用"数据的策略。
2. 大白讲解：LRU（Least Recently Used）的思路是：缓存空间有限，当满了要淘汰数据时，优先淘汰最久没被用过的那个。为什么这样设计？因为"最近被用过的数据，大概率很快还会被用"，这是缓存设计的基本假设。实现上，要同时满足"O(1) 查找"和"O(1) 移动到最近位置"两个要求：哈希表负责 O(1) 查找，双向链表负责 O(1) 的节点移动（在链表里移动一个节点只需要改指针，不用遍历）。JavaScript 里有个巧劲：`Map` 对象保证了插入顺序，可以用它来模拟链表顺序——每次访问一个 key，就把它删掉再重新插入，最老的永远在 Map 的最前面，超容时删第一个。这个技巧能用更少的代码写出 LRU，面试里很加分。
3. 漏洞卡点：只说策略，不说复杂度和实现结构。
4. 压缩总结：哈希定位 + 链表调序 + 超容淘汰。

### Q22：深拷贝面试怎么回答不翻车？
**A（费曼四段）**
1. 学习理解：深拷贝关键是边界处理，不是 API 背诵。
2. 大白讲解：面试官问深拷贝，如果你只说 `JSON.parse(JSON.stringify(obj))`，这道题基本就丢了一半分。原因是这个方法有很多边界问题：`Date` 对象会被转成字符串；`undefined`、函数、Symbol 类型的值会丢失；`Map`、`Set` 会变成空对象；最严重的是循环引用会直接报错。正确的答题路径是：先说 `JSON` 方案的局限性，再说有需要用 `lodash.cloneDeep`（成熟方案，覆盖边界全），最后如果面试官要你手写，就从递归出发，逐步补边界——先处理基础类型直接返回，再处理 `Date/RegExp/Map/Set` 等特殊类型单独处理，最后加循环引用检测（用 `WeakMap` 存已经拷贝过的对象，遇到就返回缓存而不是再递归）。这样回答显得你真正用过、踩过坑，而不是背书。
3. 漏洞卡点：只会 JSON 深拷贝。
4. 压缩总结：先讲边界，再讲方案。

### Q23：虚拟列表优化本质是什么？
**A（费曼四段）**
1. 学习理解：减少同时渲染 DOM 数量，降低布局和绘制成本。
2. 大白讲解：假设你有一个列表有 10000 条数据，如果全量渲染成 DOM，浏览器要维护 10000 个节点，每次滚动、布局、绘制的成本都非常高，页面会明显卡。虚拟列表的做法是：只渲染用户当前可以看到的区域（加上上下各一点缓冲），比如视口里只显示 20 条，那 DOM 里就只有 20 个节点；用户滚动的时候，不是真的滚动 10000 个节点，而是计算出当前偏移量，更新这 20 个节点的内容，用 CSS `transform` 把容器撑开到 10000 条应有的高度，营造出"无限长列表"的效果。有一个常见的坑：如果每条数据高度不固定（比如有些有图片有些没有），就需要动态计算每条的高度并缓存，否则滚动过程中容器高度会抖，体验很差。这种"动态高度虚拟列表"实现难度大一些，`react-window` 和 `react-virtual` 有成熟方案可以参考。
3. 漏洞卡点：忽略动态高度导致抖动。
4. 压缩总结：按视口按需渲染才是核心。

### Q24：手写题答题策略是什么？
**A（费曼四段）**
1. 学习理解：高分答案是"思路+复杂度+边界+代码验证"。
2. 大白讲解：面试手写题最大的失误是"闷头写代码，写完了一片沉默"。高分的做法应该是开口说话贯穿全程。拿到题目先别急着写，先口头梳理思路："我打算用 XX 方法，时间复杂度是 O(n)，空间复杂度是 O(1)，有没有问题？"——这一步能让面试官看到你的思维过程，即使后面代码有小 bug，思路对也能保分。写代码的时候边写边说，说清楚关键变量的含义、为什么这么设计。写完了别停，主动说边界：空数组怎么处理、null 怎么处理、负数怎么处理——这些往往是隐含的加分项。最后如果时间够，跑一遍测试用例验证，展示工程习惯。手写题考的不只是算法，也在考你平时的工作方式。
3. 漏洞卡点：闷头写代码，解释滞后。
4. 压缩总结：先框架后实现，边界一定要补。

## 五、基础快答（JS/TS/CSS/网络/Git）

### Q25：TS 里 interface 和 type 怎么选？
**A（费曼四段）**
1. 学习理解：interface 更偏对象契约，type 更偏类型组合运算。
2. 大白讲解：`interface` 和 `type` 在大多数场景下可以互换，但有几个差异值得记住。`interface` 支持声明合并——如果你在两个地方写了同名的 interface，TypeScript 会自动把它们合并成一个，这在给第三方库扩展类型时很有用；`type` 不支持合并，同名会报错。另一方面，`type` 支持联合类型、交叉类型、条件类型、映射类型这类复杂的类型运算，`interface` 做不到。实践原则：如果是描述一个对象的结构、尤其是会被别人继承或扩展的（比如组件 props、API 返回结构），优先 `interface`，语义更清晰；如果是要做类型组合运算，或者是工具类型（Partial、Pick 的变体），用 `type`。团队最重要的是统一风格，别两者随意混用，维护成本会上升。
3. 漏洞卡点：风格不统一导致维护成本上升。
4. 压缩总结：对象协议 interface，类型组合 type。

### Q26：CSS margin 塌陷怎么解释？
**A（费曼四段）**
1. 学习理解：塌陷是外边距合并规则，不是 bug。
2. 大白讲解：margin 塌陷有两种常见情形。第一种是相邻兄弟元素：两个块元素上下相邻，上面的有 `margin-bottom: 20px`，下面的有 `margin-top: 30px`，你可能以为间距是 50px，实际只有 30px——它们发生了合并，取的是较大值。第二种是父子元素：父元素没有边框或 padding，子元素的 `margin-top` 会"穿透"父元素，看起来像是父元素自己的 margin，而不是子元素的。这两种行为都是 CSS 规范定义的，不是浏览器 bug，但非常反直觉。解决方案也有规律：只要触发了 BFC（块级格式化上下文），塌陷就会消失。触发 BFC 的方式包括：给父元素加 `overflow: hidden/auto`、`display: flex/grid`、`padding` 或 `border`。实际项目里最常见的修法是给父元素加一个 `overflow: hidden` 或者改 flex 布局。
3. 漏洞卡点：只会结论，不会给解决法。
4. 压缩总结：padding/border/BFC 都能破塌陷。

### Q27：跨域为什么会发生？
**A（费曼四段）**
1. 学习理解：跨域源于浏览器同源策略，目的是安全隔离。
2. 大白讲解：同源策略是浏览器的安全机制——"协议、域名、端口"三个都一样才算同源。不同源的情况下，浏览器默认不允许页面里的 JS 读取另一个来源的响应内容，防止恶意网站偷取你的数据。这里有个重要的细节容易被误解：请求是发出去了，服务器也收到了、也返回了响应，但浏览器在收到响应之后，发现来源不符合同源策略，就把响应拦截在浏览器层不给 JS 读，并且在控制台报跨域错误。所以跨域不是"发不出去"，是"浏览器不让你读响应"。Postman 不报跨域，就是因为 Postman 不是浏览器，没有这层限制。搞清楚这一点，后续解决跨域的思路就清晰了：要么让服务端在响应头里告诉浏览器"我允许你读"（CORS），要么用代理绕过浏览器的限制。
3. 漏洞卡点：把跨域问题当后端故障。
4. 压缩总结：跨域是浏览器安全策略问题。

### Q28：Git rebase 和 merge 的边界？
**A（费曼四段）**
1. 学习理解：merge 保留分叉历史，rebase 重写提交基线。
2. 大白讲解：`merge` 是把两条分支的历史合并，会产生一个新的 merge commit，历史图里会有分叉和汇合，完整保留了"谁在什么时候从哪里拉的分支、在哪里合回来的"。`rebase` 是把你在自己分支上的提交，"接"到目标分支的最新位置上，历史看起来是线性的，但实际上你的提交被重写了（commit hash 变了）。个人分支上用 rebase 整理提交，让历史更清晰，这是推荐的做法；但如果把一个已经 push 到远端、其他人也在用的分支 rebase，会导致别人本地的历史和远端对不上，强推的话会把别人的提交搞乱，这是团队里最容易引发矛盾的 Git 操作。所以记住一条铁律：已经公开的提交历史不能 rebase，只在本地未推送或个人私有分支上用。
3. 漏洞卡点：对已共享分支强制 rebase。
4. 压缩总结：私有可重写，公共慎重写。

### Q29：HTTP 状态码如何用于排障？
**A（费曼四段）**
1. 学习理解：状态码是故障分层入口：4xx 多查请求，5xx 多查服务。
2. 大白讲解：状态码是排障的第一道线索，不同数字段代表不同方向。`2xx` 说明正常，不用管；`3xx` 是重定向，要看是不是跳到了不期望的地方。`4xx` 是客户端问题：`401` 是没有认证、token 失效了；`403` 是有认证但没权限，要查权限配置；`404` 是路径不对，先查 URL 和请求参数；`429` 是被限流了，要查接口频次。`5xx` 是服务端问题：`500` 要去看服务日志，一般是代码抛异常；`502/504` 是网关或上游服务挂了，要查服务健康状态和超时配置。排障时一定先看状态码定方向，然后结合请求的 Header、Body、时间戳再细查，不要上来就盲猜。
3. 漏洞卡点：不分层直接盲查。
4. 压缩总结：先分层后定位，状态码是第一线索。

### Q30：TCP 三次握手怎么讲透？
**A（费曼四段）**
1. 学习理解：三次握手是双方确认收发能力和序列号，建立可靠连接。
2. 大白讲解：为什么要三次而不是两次？两次握手只能让服务端确认"客户端能发、我能收"，但客户端不能确认"服务端能发、我能收"——万一服务端的回复丢了，客户端不知道，连接就建立不起来。三次握手的流程是：客户端发一个 SYN（我想连接，我的序列号是 X），服务端回一个 SYN+ACK（我收到了，我的序列号是 Y，确认你的是 X+1），客户端再回一个 ACK（我收到了，确认你的是 Y+1）。到这里，双方都确认了自己的发送能力和对方的接收能力，序列号也同步好了，连接建立。四次挥手是断开连接，双方都要各自确认"我发完了"，所以比握手多一次。面试里背步骤不够，能说清楚"为什么是三次而不是两次"才是真的理解了。
3. 漏洞卡点：只背术语不讲目的。
4. 压缩总结：三次握手是可靠连接的前置确认机制。
