## 📋 第一性原理：Java vs JavaScript 底层对比表

### 1. 并发模型对比（核心中的核心）

| 维度 | Java（多线程同步） | JavaScript（单线程异步） | 面试必答点 |
|------|-------------------|------------------------|-----------|
| **执行模型** | 多线程并行执行 | 单线程 + Event Loop | "JS是单线程，但通过异步I/O实现并发" |
| **阻塞处理** | 线程阻塞，其他线程继续 | 主线程阻塞，所有请求卡死 | "CPU密集任务会阻塞Event Loop" |
| **并发控制** | synchronized、Lock | Promise、async/await | "JS没有锁，靠原子操作和队列" |
| **内存模型** | 堆内存共享，栈内存隔离 | 单一堆栈，闭包持有引用 | "闭包可能导致内存泄漏" |
| **错误处理** | try-catch捕获同步异常 | try-catch + .catch()捕获异步 | "未捕获的Promise rejection会崩溃" |
| **典型场景** | 数据库连接池、线程池 | 事件驱动、非阻塞I/O | "Node.js适合I/O密集，不适合CPU密集" |

**面试话术模板**：
> "在Java中，我们用线程池处理并发请求，每个请求独立执行。但在Node.js中，如果我在一个请求里执行了大量计算（比如加密算法），会直接阻塞Event Loop，导致所有用户的请求都卡住。所以我会把CPU密集任务放到Worker Threads或后端Java服务处理。"

### 2. Event Loop 深度解析（必考）

#### 2.1 宏任务 vs 微任务

| 类型 | 包含内容 | 执行时机 | Java类比 |
|------|---------|---------|---------|
| **宏任务** | setTimeout、setInterval、I/O | 每轮Event Loop执行一个 | 类似线程池的任务队列 |
| **微任务** | Promise.then、queueMicrotask | 当前宏任务结束后立即清空 | 类似线程内的优先级队列 |

**执行顺序**：
```
1. 执行同步代码
2. 清空所有微任务队列
3. 执行一个宏任务
4. 重复步骤2-3
```

**经典面试题**：
```javascript
console.log('1');

setTimeout(() => {
  console.log('2');
  Promise.resolve().then(() => console.log('3'));
}, 0);

Promise.resolve().then(() => {
  console.log('4');
  setTimeout(() => console.log('5'), 0);
});

console.log('6');

// 输出顺序：1 6 4 2 3 5
```

**面试话术**：
> "这道题考察的是微任务优先级。第一轮：同步代码1、6；清空微任务4；执行宏任务2，产生微任务3，立即执行；第二轮：执行宏任务5。关键是理解'微任务插队'的机制。"

#### 2.2 Node.js Event Loop 六阶段

| 阶段 | 作用 | 典型API | 面试考点 |
|------|------|---------|---------|
| timers | 执行setTimeout/setInterval | setTimeout | 最小延迟不是0ms |
| pending callbacks | 执行I/O回调 | fs.readFile | 异步I/O的回调在这里 |
| idle, prepare | 内部使用 | - | 可忽略 |
| poll | 等待新的I/O事件 | 网络请求 | 最重要的阶段 |
| check | 执行setImmediate | setImmediate | 比setTimeout优先 |
| close callbacks | 关闭回调 | socket.on('close') | 资源清理 |

**面试必答**：
> "在Next.js的Server Actions中，如果我执行了大量的数据库查询，这些异步I/O会在poll阶段等待。如果某个查询特别慢（比如没加索引），会阻塞整个Event Loop，导致其他用户的请求无法进入。所以我会用数据库连接池 + 超时控制。"

### 3. Promise 并发控制（金融场景必备）

#### 3.1 Promise API对比

| API | 行为 | 适用场景 | 面试考点 |
|-----|------|---------|---------|
| Promise.all | 全部成功才resolve，一个失败就reject | 所有请求都必须成功 | 金融场景慎用 |
| Promise.allSettled | 等待全部完成，返回每个结果 | 对账、批量查询 | **推荐** |
| Promise.race | 第一个完成就返回 | 超时控制 | 配合timeout使用 |
| Promise.any | 第一个成功就返回 | 多数据源降级 | 少用 |

**经典场景：批量对账**
```typescript
// ❌ 错误：一个失败全失败
const results = await Promise.all([
  checkAccount1(),
  checkAccount2(),
  checkAccount3()
]);

// ✅ 正确：全部执行完再处理
const results = await Promise.allSettled([
  checkAccount1(),
  checkAccount2(),
  checkAccount3()
]);

results.forEach((result, index) => {
  if (result.status === 'fulfilled') {
    console.log(`账户${index}对账成功`);
  } else {
    console.error(`账户${index}对账失败:`, result.reason);
  }
});
```

#### 3.2 并发数控制（手写必考）

**场景**：同时调用100个银行接口，但最多只能3个并发，防止打爆后端。

```typescript
async function concurrentLimit<T>(
  tasks: (() => Promise<T>)[],
  limit: number
): Promise<T[]> {
  const results: T[] = [];
  const executing: Promise<void>[] = [];

  for (const [index, task] of tasks.entries()) {
    const promise = task().then(result => {
      results[index] = result;
    });

    executing.push(promise);

    if (executing.length >= limit) {
      await Promise.race(executing);
      executing.splice(
        executing.findIndex(p => p === promise),
        1
      );
    }
  }

  await Promise.all(executing);
  return results;
}

// 使用
const tasks = Array.from({ length: 100 }, (_, i) => 
  () => fetch(`/api/account/${i}`)
);

const results = await concurrentLimit(tasks, 3);
```

**面试话术**：
> "这个并发控制器的核心是用Promise.race等待最快完成的那个，然后从executing数组中移除，给新任务腾位置。这样保证同时最多只有3个请求在跑。在光大银行项目中，我用这个方案批量查询千万级流水，避免了数据库连接池耗尽。"

### 4. 内存管理对比

| 维度 | Java | JavaScript | 面试考点 |
|------|------|-----------|---------|
| **垃圾回收** | 分代回收（Young/Old） | 标记清除 + 增量标记 | "V8的GC策略" |
| **内存泄漏** | ThreadLocal未清理 | 闭包持有引用 | "两者都会泄漏" |
| **排查工具** | jmap、MAT | Chrome DevTools、heapdump | "实战经验" |
| **典型场景** | 大对象进Old区 | 全局变量、定时器 | "如何避免" |

#### 4.1 JavaScript内存泄漏典型场景

**场景1：闭包持有DOM引用**
```javascript
// ❌ 内存泄漏
function createLeak() {
  const largeData = new Array(1000000);
  
  return function() {
    console.log(largeData.length); // 闭包持有largeData
  };
}

const leak = createLeak(); // largeData永远不会被回收

// ✅ 正确
function createNoLeak() {
  const largeData = new Array(1000000);
  const length = largeData.length;
  
  return function() {
    console.log(length); // 只持有基本类型
  };
}
```

**场景2：定时器未清理**
```javascript
// ❌ 内存泄漏
useEffect(() => {
  const timer = setInterval(() => {
    console.log('tick');
  }, 1000);
  // 忘记清理
}, []);

// ✅ 正确
useEffect(() => {
  const timer = setInterval(() => {
    console.log('tick');
  }, 1000);
  
  return () => clearInterval(timer); // 组件卸载时清理
}, []);
```

**面试话术**：
> "在Java中，我遇到过ThreadLocal内存泄漏，需要在finally中调用remove()。在JavaScript中，最常见的是闭包持有大对象引用。比如在React组件中，如果useEffect的依赖数组写错，会导致旧的闭包一直持有引用。我的排查方法是用Chrome DevTools的Heap Snapshot对比前后内存，找到Detached DOM节点。"

### 5. 异步错误处理对比

| 场景 | Java | JavaScript | 最佳实践 |
|------|------|-----------|---------|
| **同步错误** | try-catch | try-catch | 一致 |
| **异步错误** | Future.get() | .catch() / try-catch | 必须捕获 |
| **全局捕获** | Thread.UncaughtExceptionHandler | process.on('unhandledRejection') | 兜底方案 |
| **错误传播** | throws声明 | Promise链式传递 | 不同机制 |

#### 5.1 JavaScript异步错误捕获

**场景1：Promise错误**
```typescript
// ❌ 错误：未捕获的rejection
async function dangerousCode() {
  const data = await fetch('/api/data'); // 如果失败，整个进程可能崩溃
  return data.json();
}

// ✅ 正确：捕获错误
async function safeCode() {
  try {
    const data = await fetch('/api/data');
    return await data.json();
  } catch (error) {
    console.error('请求失败:', error);
    return null; // 返回降级数据
  }
}
```

**场景2：Next.js全局错误处理**
```typescript
// app/error.tsx
'use client';

export default function Error({
  error,
  reset,
}: {
  error: Error & { digest?: string };
  reset: () => void;
}) {
  useEffect(() => {
    // 上报到Sentry
    console.error(error);
  }, [error]);

  return (
    <div>
      <h2>出错了</h2>
      <button onClick={reset}>重试</button>
    </div>
  );
}
```

**面试话术**：
> "在Java中，我们用try-catch捕获同步异常，用Future.get()捕获异步异常。在JavaScript中，async/await让异步代码看起来像同步，但本质还是Promise。如果不加try-catch，未捕获的rejection会触发unhandledRejection事件，在Node.js中可能导致进程退出。所以我在Next.js项目中，会用error.tsx统一捕获，并上报到Sentry。"

## 🎯 面试"降维打击"话术模板

### 1. Event Loop问题

**面试官问**："请说一下JavaScript的事件循环机制。"

**满分回答**：
> "以前在做Java开发时，我们解决并发靠的是多线程协作和锁机制。但JavaScript的第一性原理是**单线程非阻塞I/O**。
> 
> 它的事件循环分为宏任务和微任务。宏任务包括setTimeout、I/O，每轮Event Loop执行一个；微任务包括Promise.then，在当前宏任务结束后立即清空。
> 
> 但我更看重它在**Node.js服务端渲染(SSR)**时的表现。比如在Next.js里，如果我们在一个渲染循环中执行了大量的计算逻辑（CPU密集型），它会直接阻塞Event Loop，导致所有用户的请求都无法进入。
> 
> 针对这种情况，我会利用Worker Threads处理重计算，或者在后端Java层通过异步队列处理。这种'非阻塞'的思维是我从Java转型全栈时感受最深的地方。"

### 2. Promise并发控制

**面试官问**："如何实现一个Promise并发数控制器？"

**满分回答**：
> "这个问题我在光大银行项目中遇到过。我们需要批量查询100个账户的流水，但如果同时发起100个请求，会把数据库连接池打爆。
> 
> 我的解决方案是用Promise.race实现并发控制：维护一个executing数组，最多放3个Promise；每当一个完成，就从数组中移除，给新任务腾位置。
> 
> 核心代码是：
> ```typescript
> if (executing.length >= limit) {
>   await Promise.race(executing);
>   executing.splice(executing.findIndex(p => p === promise), 1);
> }
> ```
> 
> 这样保证同时最多只有3个请求在跑，既提升了效率，又不会压垮后端。"

### 3. 内存泄漏排查

**面试官问**："你如何排查JavaScript的内存泄漏？"

**满分回答**：
> "我在Java和JavaScript中都遇到过内存泄漏。Java中最常见的是ThreadLocal未清理，JavaScript中最常见的是闭包持有大对象引用。
> 
> 排查方法类似：
> - Java用jmap dump堆内存，然后用MAT分析
> - JavaScript用Chrome DevTools的Heap Snapshot，对比前后内存
> 
> 具体步骤：
> 1. 操作前拍一次快照
> 2. 执行可能泄漏的操作（比如打开关闭组件10次）
> 3. 手动触发GC
> 4. 再拍一次快照，对比差异
> 5. 找到Detached DOM节点或持续增长的对象
> 
> 在OmniSettlement项目中，我发现WebSocket连接未正确关闭，导致每次重连都会创建新的监听器。修复方法是在组件卸载时调用socket.close()并移除所有监听器。"

## 🧠 异步代码执行顺序推导（必练）

### 题目1：基础版

```javascript
console.log('1');

setTimeout(() => {
  console.log('2');
  Promise.resolve().then(() => console.log('3'));
}, 0);

Promise.resolve().then(() => {
  console.log('4');
  setTimeout(() => console.log('5'), 0);
});

console.log('6');
```

**答案**：1 6 4 2 3 5

**推导过程**：
1. 同步代码：1、6
2. 清空微任务：4（产生宏任务5）
3. 执行宏任务：2（产生微任务3）
4. 清空微任务：3
5. 执行宏任务：5

### 题目2：进阶版

```javascript
async function async1() {
  console.log('async1 start');
  await async2();
  console.log('async1 end');
}

async function async2() {
  console.log('async2');
}

console.log('script start');

setTimeout(() => {
  console.log('setTimeout');
}, 0);

async1();

new Promise(resolve => {
  console.log('promise1');
  resolve();
}).then(() => {
  console.log('promise2');
});

console.log('script end');
```

**答案**：
```
script start
async1 start
async2
promise1
script end
async1 end
promise2
setTimeout
```

**关键点**：
- `await async2()` 等价于 `Promise.resolve(async2()).then(() => console.log('async1 end'))`
- Promise构造函数中的代码是同步执行的
