# 需求描述：
# 商品搜索页 — 防抖节流面试实战需求
## 一、核心目标
通过极简的商品搜索页场景，覆盖防抖/节流核心应用场景，聚焦**手写实现、场景判断、原理讲解**三大面试核心。

## 二、技术栈
React 19 + TypeScript，核心要求：手写 `useDebounce` 和 `useThrottle` 自定义 Hook。

## 三、页面描述
单页商品搜索界面：顶部搜索框（支持联想）、下方商品列表（支持滚动加载），适配窗口尺寸变化。

## 四、核心功能需求
### 1. 搜索联想（防抖 · 500ms）
- **触发场景**：用户在搜索框输入关键词
- **核心规则**：停止输入 500ms 后请求联想词；输入过程不发请求，继续输入则重新计时
- **边界处理**：组件卸载时清理定时器
- **选型依据**：仅关心最终输入结果，中间按键无需响应

### 2. 滚动加载更多（节流 · 300ms）
- **触发场景**：商品列表向下滚动至接近底部
- **核心规则**：每 300ms 检测一次是否触底；加载中加锁，防止重复请求
- **选型依据**：滚动过程中需持续检测，不能等滚动停止

### 3. 窗口 resize 重算布局（防抖 · 300ms）
- **触发场景**：拖动窗口调整尺寸
- **核心规则**：停止拖动 300ms 后重新计算列表布局
- **选型依据**：仅关心最终窗口尺寸，中间调整状态无意义

## 五、场景汇总表
| 功能场景       | 触发事件 | 策略   | 延迟   | 核心判断依据         |
|----------------|----------|--------|--------|----------------------|
| 搜索联想       | input    | 防抖   | 500ms  | 仅需最终输入结果     |
| 滚动加载更多   | scroll   | 节流   | 300ms  | 过程中需持续响应     |
| 窗口 resize 布局 | resize   | 防抖   | 300ms  | 仅需最终窗口尺寸     |

> 核心判断口诀：**要结果用防抖，要过程用节流**

# 拆解需求：


## 节流在这里作用


### 检测滚动是否触底

这个问题很好，我来解释清楚。

在古代300ms检测是否触底操作 避免频繁操作，浏览器scroll触发既然无法避免就控制执行。

简单说：已滚动距离 + 可视区高度 ≥ 内容总高度，就是触底了。

三个值：
- `scrollTop` — 已经滚上去多少
- `clientHeight` — 可视区有多高
- `scrollHeight` — 内容总高度

判断：`scrollHeight - scrollTop - clientHeight < 50` → 离底部不到 50px，触发加载。




滚动事件和节流的关系是这样的：

当你在商品列表里滚动时，浏览器每秒会触发几十甚至上百次 `scroll` 事件。每次触发都要去计算"是否滚到底部了？要不要加载下一页？"。如果不做节流，这个计算每秒执行几十次，完全没必要，浪费性能。

加了节流（300ms）之后，不管你滚得多快，这个"是否触底"的检测最多每 300ms 执行一次。

打个比方：
- 没有节流：你滚动 1 秒，浏览器检查了 60 次"到底了没？到底了没？到底了没？..."
- 有节流（300ms）：你滚动 1 秒，浏览器只检查了 3 次"到底了没？"

右侧日志面板里的 `(原始47次 → 节流5次)` 就是在展示这个对比 — scroll 事件原始触发了 47 次，但实际只执行了 5 次检测。

为什么不用防抖？因为防抖要等你停止滚动才执行。如果用防抖，你一直在滚，它就一直不检测，等你停下来才检测一次 — 那用户体验就很差，明明已经滚到底了，还要等停下来才加载。节流保证滚动过程中持续检测，只是降低了频率。

这就是需求里说的口诀：**要结果用防抖（搜索只关心最终输入），要过程用节流（滚动过程中要持续检测）**。



### 内容总高度是什么


是当前已加载并渲染到 DOM 里的数据的高度，不是固定 100 条。

比如第一页加载了 12 条，scrollHeight 就是这 12 条卡片撑起来的高度。滚到底触发加载，变成 24 条，scrollHeight 就变大了。随着不断加载，scrollHeight 持续增长，直到所有数据都加载完。

所以 scrollHeight 是动态的，取决于当前渲染了多少条数据。




### 闭包陷阱


对，闭包陷阱是这个项目里一个很重要的面试考点，代码里已经体现了。

防抖节流的本质就是 `setTimeout`。你传给 `setTimeout` 的回调函数，闭包捕获的永远是创建时的变量快照，闭包陷阱就是 react每次重新渲染如果不用useRef包裹就会拿到旧的state

**inner函数锁住外层outer函数的变量是锁的被创建时所在环境的变量；**


![zs1020-useRef解决闭包陷阱](zs1020-useRef解决闭包陷阱.md)




项目中涉及闭包陷阱的地方有两层：

1. **Hook 层面**（`useDebounce` / `useThrottle`）：
   - 用 `callbackRef.current = fn` 始终指向最新回调，避免 `setTimeout` / 时间戳判断里捕获到旧的 state/props
   - 如果直接用 `useCallback` 包裹 fn，闭包会锁死创建时的变量快照，导致防抖/节流回调里拿到的是过期数据

2. **业务层面**（`App.jsx` 的滚动加载）：
   - `page`、`hasMore`、`loading` 这些 state 在节流回调里会被闭包捕获旧值
   - 所以用了 `pageRef`、`hasMoreRef`、`loadingRef` 三个 ref 同步最新值，节流回调里读 ref 而不是直接读 state
   - 这是 React 中定时器/事件回调的经典闭包陷阱场景

面试时可以这样讲：「防抖节流的核心难点不是定时器逻辑本身，而是在 React 函数组件里如何避免闭包陷阱。我用 useRef 存最新回调和最新状态，确保异步回调里永远拿到最新值。
