## 滚动暴力渲染组件时候 每次滚动会触发渲染吗



不是的。暴力渲染滚动时**不会**重复渲染 10000 个列表。 ^ys80k1

这是 BruteList 和 VirtualList 的核心区别：

**BruteList（暴力渲染）：**
- 首次渲染时一次性把 10000 个 DOM 节点全部创建好
- 滚动时是浏览器原生的 CSS `overflow: auto` 滚动，**不触发任何 React 重渲染**
- 浏览器只是移动已有 DOM 的可视区域，GPU 合成层处理，非常快
- 所以滚动时 React Profiler 不会显示 BruteList 在渲染 — 这是正确的

**VirtualList（虚拟列表）：**
- 首次渲染只创建 ~20 个 DOM 节点
- 滚动时 `onScroll` → `setScrollTop` → React 重渲染 → 重新计算可视区 → 替换 DOM 内容
- 所以滚动时 VirtualList **会**触发 React 重渲染

**暴力渲染的性能问题不在滚动，而在：**
1. 首次渲染慢 — 一次性创建 10000 个 DOM 节点，耗时几百毫秒
2. 内存占用大 — 10000 个 DOM 节点常驻内存
3. 搜索/过滤时慢 — data 变化要重新渲染 10000 个 DOM

所以你在 Profiler 里看到滚动 BruteList 时是 App 在渲染（因为 FPS 计时器），而不是 BruteList 在渲染 — 这其实是对的。BruteList 滚动确实不触发 React 重渲染。

现在回到你说的两个 bug：

1. **App 在渲染** — 是 FPS 计时器 `setFps` 每秒触发的，和滚动无关。可以把 FPS 抽成独立组件解决。
2. **更新渲染 0ms** — 这是 `dataChangedRef` 逻辑的问题，需要加日志实证。

## 暴力渲染与虚拟列表渲染时机


对，你理解得完全正确。

暴力渲染（BruteList）：
- 滚动不触发 React 重渲染 — 10000 个 DOM 节点已经全部在页面上了，滚动只是浏览器原生的 CSS `overflow: auto` 滚动，纯 GPU 合成，React 完全不参与
- 只有搜索（data prop 变化）才会触发 React 重渲染，重新 `.map()` 生成新的 DOM

虚拟列表（VirtualList）：
- 滚动会触发 React 重渲染 — 因为 `onScroll` 回调里 `setState` 更新了 `scrollTop`，hook 重新计算可视区的 `startIndex/endIndex`，React 需要重新渲染那十几个可见的 DOM 节点
- 搜索也会触发重渲染 — data prop 变化，同样需要重新计算可视区

这也是为什么之前 Bug #3 里滚动帧耗时暴力渲染反而更低（0.4ms vs 0.9ms）的原因 — 暴力渲染滚动时 React 啥都没干，虚拟列表滚动时 React 要干活。但虚拟列表的优势在首次渲染速度（131ms vs 0.3ms）和内存占用（10000 DOM vs 14 DOM）。 ^5m6g5j
