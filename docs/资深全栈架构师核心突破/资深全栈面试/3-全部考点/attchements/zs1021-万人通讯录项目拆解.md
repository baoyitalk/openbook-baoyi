## 滚动暴力渲染组件时候 每次滚动会触发渲染吗



不是的。暴力渲染滚动时**不会**重复渲染 10000 个列表。 ^ys80k1

这是 BruteList 和 VirtualList 的核心区别：

**BruteList（暴力渲染）：**
- 首次渲染时一次性把 10000 个 DOM 节点全部创建好
- 滚动时是浏览器原生的 CSS `overflow: auto` 滚动，**不触发任何 React 重渲染**
- 浏览器只是移动已有 DOM 的可视区域，GPU 合成层处理，非常快
- 所以滚动时 React Profiler 不会显示 BruteList 在渲染 — 这是正确的

**VirtualList（虚拟列表）：**
- 首次渲染只创建 ~20 个 DOM 节点
- 滚动时 `onScroll` → `setScrollTop` → React 重渲染 → 重新计算可视区 → 替换 DOM 内容
- 所以滚动时 VirtualList **会**触发 React 重渲染

**暴力渲染的性能问题不在滚动，而在：**
1. 首次渲染慢 — 一次性创建 10000 个 DOM 节点，耗时几百毫秒
2. 内存占用大 — 10000 个 DOM 节点常驻内存
3. 搜索/过滤时慢 — data 变化要重新渲染 10000 个 DOM

所以你在 Profiler 里看到滚动 BruteList 时是 App 在渲染（因为 FPS 计时器），而不是 BruteList 在渲染 — 这其实是对的。BruteList 滚动确实不触发 React 重渲染。

现在回到你说的两个 bug：

1. **App 在渲染** — 是 FPS 计时器 `setFps` 每秒触发的，和滚动无关。可以把 FPS 抽成独立组件解决。
2. **更新渲染 0ms** — 这是 `dataChangedRef` 逻辑的问题，需要加日志实证。

## 暴力渲染与虚拟列表渲染时机


对，你理解得完全正确。

暴力渲染（BruteList）：
- 滚动不触发 React 重渲染 — 10000 个 DOM 节点已经全部在页面上了，滚动只是浏览器原生的 CSS `overflow: auto` 滚动，纯 GPU 合成，React 完全不参与
- 只有搜索（data prop 变化）才会触发 React 重渲染，重新 `.map()` 生成新的 DOM

虚拟列表（VirtualList）：
- 滚动会触发 React 重渲染 — 因为 `onScroll` 回调里 `setState` 更新了 `scrollTop`，hook 重新计算可视区的 `startIndex/endIndex`，React 需要重新渲染那十几个可见的 DOM 节点
- 搜索也会触发重渲染 — data prop 变化，同样需要重新计算可视区

这也是为什么之前 Bug #3 里滚动帧耗时暴力渲染反而更低（0.4ms vs 0.9ms）的原因 — 暴力渲染滚动时 React 啥都没干，虚拟列表滚动时 React 要干活。但虚拟列表的优势在首次渲染速度（131ms vs 0.3ms）和内存占用（10000 DOM vs 14 DOM）。 ^5m6g5j




## 搜索触发暴力渲染是按照过滤结果的所有dom


暴力渲染搜索时是"按过滤结果全量渲染"，不是加载所有 10000 条 DOM。

具体流程：

1. App.jsx 中 `filteredData = useMemo(() => contacts.filter(...), [filterText])`
2. 搜索"王"时，`filteredData` 只包含名字/部门/手机号含"王"的联系人（比如 500 条）
3. `filteredData` 作为 `data` prop 传给 BruteList
4. BruteList 对 `data.map()` 全量渲染 → 生成 500 个 DOM 节点（不是 10000 个）

所以暴力渲染的"暴力"体现在：**对过滤后的结果集，全部生成 DOM**。搜索"王"得到 500 条，就渲染 500 个 DOM；清空搜索框，就渲染全部 10000 个 DOM。

对比虚拟列表：搜索"王"得到 500 条，但只渲染可视区的 ~14 个 DOM。

这也是为什么搜索后暴力渲染的"搜索渲染"耗时会比首次渲染低——因为数据量变少了，DOM 数量也少了。你可以在面板上看到 DOM 节点数会跟着搜索结果变化。 ^8zb92t




## 核心原理

虚拟列表就一句话：**眼睛看不到的，就不渲染。**

从第一性原理拆：

**问题**：10000 条数据 → 10000 个 DOM → 浏览器卡死

**本质原因**：DOM 太多。不是数据太多，是 DOM 太多。

**关键洞察**：屏幕就那么大，用户同时只能看到 ~8 条。剩下 9992 条 DOM 白白占内存。

**解法**：只渲染用户能看到的那 8 条（+ 上下各 5 条缓冲防白屏）= 18 个 DOM。

**怎么做到的**：3 步

```
1. 算位置：scrollTop ÷ 行高 = 第几条在最上面（startIndex）
2. 切数据：data.slice(startIndex, endIndex) 只取可视区那几条
3. 骗滚动条：外层容器撑一个 totalHeight = 10000 × 行高 的空 div，让滚动条看起来像有 10000 条
```

**类比**：电影院放电影。胶片有 10000 帧，但放映机同一时刻只投射 1 帧到屏幕上。虚拟列表就是那个放映机——数据是胶片，DOM 是屏幕上的画面，滚动条是进度条。

记住这个公式就够了：
```
startIndex = Math.floor(scrollTop / itemHeight)
```
一切都从这一行推导出来。

想象一个卷轴，每行高 60px：

```
第 0 条：0px   ~ 60px
第 1 条：60px  ~ 120px
第 2 条：120px ~ 180px
第 3 条：180px ~ 240px
...
```

`scrollTop` 就是你滚了多远。比如你往下滚了 150px，那 `scrollTop = 150`。

问题来了：**滚了 150px，屏幕最上面露出的是第几条？**

```
150 ÷ 60 = 2.5 → 向下取整 = 2
```

答案：第 2 条（从 120px 开始那条）。它被滚上去了一半（30px），但还露着下半部分。

就这么简单：
- `scrollTop` = 滚了多远（浏览器告诉你的）
- `itemHeight` = 每行多高（你定的，60px） ^vbcwni
- 除一下，取整 = 第几条在最上面

知道了"第几条在最上面"，就知道该渲染哪几条了。



## fiber架构体现在你主动调用和隐式使用中

### 场景1：显示调用
Fiber 在这个项目里体现在搜索场景，具体就是 App.jsx 里的 `useTransition` + `startTransition`。

**问题场景**：用户在搜索框输入"王"

这时候有两件事要做：
1. 输入框显示"王"（高优先级，用户要看到自己打了什么）
2. 过滤 10000 条数据 + 暴力渲染匹配结果（低优先级，慢点没关系）

**没有 Fiber 时**（关闭 startTransition）：
```
输入"王" → setFilterText("王") → 过滤数据 → 暴力渲染 500 个 DOM → 完成
                                    ↑ 这一步阻塞主线程 200ms+
                                    ↑ 输入框卡死，用户以为没反应
```
两件事排队做，第 2 件太慢，把第 1 件堵住了。

**有 Fiber 时**（开启 startTransition）：
```
输入"王" → setInputValue("王") → 输入框立即显示 ✅
         → startTransition(() => setFilterText("王"))
           → Fiber 把过滤+渲染拆成小块
           → 每个小块做完检查：有没有新的用户输入？
           → 有 → 丢掉当前工作，先处理输入
           → 没有 → 继续下一块，直到完成
```

**一句话总结**：Fiber 让 React 能"分期付款"——把一个大渲染任务拆成小块，每块之间检查有没有更紧急的事（用户输入），有就先干紧急的。

**和虚拟列表的关系**：
- 虚拟列表 = 少买东西（减少 DOM 数量，从根源降低工作量）
- Fiber 时间切片 = 分期付款（工作量不变，但不一次性阻塞）
- 两者互补：虚拟列表解决"渲染太多 DOM"，Fiber 解决"即使 DOM 少了，过滤 10000 条数据本身也需要时间"

项目里你可以实际体验：点那个开关按钮关掉 startTransition，然后快速输入，输入框会明显卡顿。开启后就丝滑了。


### 场景2：基础隐式使用


不是，Fiber 架构在这个项目里有两层体现：

**显式体现**（你写的代码直接用了）：
- `useTransition` + `startTransition` — 搜索框那个开关演示

**隐式体现**（Fiber 在底层默默工作，你没写但它在）：

1. **虚拟列表滚动时**：每次滚动触发 `setScrollTop` → React 需要 diff 可视区的 ~18 个 DOM 节点。Fiber 把这个 diff 过程变成可中断的——如果滚动太快，React 可以丢弃还没 commit 的中间帧，直接跳到最新的 scrollTop 对应的状态。这就是为什么虚拟列表滚动不卡。

2. **React.Profiler 的 `actualDuration`**：这个值就是 Fiber 架构提供的。Fiber 给每个组件的 Fiber 节点记录了渲染耗时，Profiler 才能精确报告"这个组件花了多少 ms"。没有 Fiber 架构，你拿不到这个数据。

3. **React.memo 的浅比较跳过**：Fiber 在 reconciliation 阶段检查 memo 组件的 props 是否变化，没变就跳过整棵子树。这也是 Fiber 架构的能力。

4. **key 优化**：`key={item.id}` 让 Fiber 在 diff 列表时能复用已有的 Fiber 节点，而不是销毁重建。

所以更准确地说：`startTransition` 是你**主动调用** Fiber 能力的地方，但 Fiber 架构在整个项目的每一次渲染、diff、跳过、计时中都在工作。面试时可以这样说：

> "项目里 startTransition 是显式使用 Fiber 时间切片的地方，但 Fiber 架构其实贯穿整个项目——虚拟列表的高频滚动更新、Profiler 的精确计时、memo 的跳过渲染、key 的节点复用，底层都是 Fiber 在驱动。"




### ascII绘图展示

来，先看老架构（React 15），再看 Fiber，对比就懂了。

**老架构：一口气干完，不能停**
```
用户输入"王"
    │
    ▼
┌─────────────────────────────────────────────┐
│  递归渲染（不可中断）                          │
│                                             │
│  App → BruteList → 第1条 → 第2条 → ... → 第500条  │
│  ════════════════════════════════════════    │
│  ▲ 一条线走到底，中间不能停                     │
│  ▲ 耗时 200ms，主线程被占满                    │
│  ▲ 用户再输入"五"？对不起，等着，我忙着呢        │
└─────────────────────────────────────────────┘
    │
    ▼
  页面更新（用户感觉：卡了 200ms）
```

**Fiber 架构：切成小块，随时能停**
```
用户输入"王"
    │
    ▼
┌──────────┐  ┌──────────┐  ┌──────────┐
│ 小块 1    │→│ 小块 2    │→│ 小块 3    │→ ...
│ 渲染 1-50 │  │ 渲染51-100│  │渲染101-150│
│  5ms      │  │  5ms      │  │  5ms      │
└──────────┘  └──────────┘  └──────────┘
      │              │              │
      ▼              ▼              ▼
   检查一下：      检查一下：      检查一下：
   有急事吗？      有急事吗？      有急事吗？
   没有→继续       没有→继续       ⚠️ 用户输入了"五"！
                                     │
                                     ▼
                              丢掉剩余工作
                              先处理"王五"的输入
                              输入框立即响应 ✅
                                     │
                                     ▼
                              重新开始渲染"王五"的结果
```

^p8ity7

**Fiber 节点长啥样（链表结构）**
```
        App (Fiber节点)
        │
   ┌────┴────┐
   ▼         ▼
BruteList  VirtualList     ← child 指针
   │         │
   ▼         ▼
  第1条  →  第2条  →  第3条   ← sibling 指针（兄弟链表）
   │
   ▼
  <span>     ← child 指针（往下）
   │
   ▼
  return → 第1条             ← return 指针（往上回去）
```

每个 Fiber 节点有 3 个指针：`child`（第一个孩子）、`sibling`（下一个兄弟）、`return`（父节点）。

老架构用递归（调用栈），进去了就出不来。Fiber 用链表，处理完一个节点，顺着指针走到下一个，**随时可以停下来**，记住走到哪了，回头再继续。

**一句话**：Fiber = 把递归树遍历改成链表遍历，这样就能暂停、恢复、丢弃。
