## 第一性原理：性能问题的本质

性能卡顿只有两个根因：
1. **做的次数太多**（触发频率问题）
2. **做一次太慢**（单次执行时间问题）

防抖节流解决第 1 个，Fiber 解决第 2 个。 ^5qsdsa

---

## 一、防抖（Debounce）

**原理**：等你停下来再做。

```
用户输入：  王    王五    王五六    王五六七
时间轴：   ──┬─────┬──────┬────────┬──────────────
              │     │      │        │
              │     │      │        └─ 300ms 没新输入了
              │     │      │                │
              ×     ×      ×                ▼
           取消   取消   取消          执行！过滤"王五六七"

结果：4 次输入 → 只执行 1 次
```

**类比**：电梯关门。有人进来就重新等 3 秒，没人了才关门。

---

## 二、节流（Throttle）

**原理**：固定频率做，不管你触发多少次。

```
用户滚动：  ↓↓↓↓↓↓↓↓↓↓↓↓↓↓↓↓↓↓↓↓↓↓↓↓↓↓↓↓↓↓
时间轴：   ──┬────────┬────────┬────────┬──────
              │        │        │        │
              ▼        ▼        ▼        ▼
           执行1     执行2     执行3     执行4
           (16ms)   (16ms)   (16ms)   (16ms)

结果：30 次滚动事件 → 只执行 4 次（每 16ms 一次 = rAF 节流）
```

**类比**：地铁发车。不管站台多少人，每 3 分钟发一班。

---

## 三、Fiber 时间切片

**原理**：一次太慢？拆成小块，穿插着做。

```
没有 Fiber：
主线程：|◄────── 渲染 200ms ──────►|响应输入|画面|
         ▲ 这 200ms 内用户操作全部卡死

有 Fiber：
主线程：|渲5ms|空|渲5ms|空|输入！|处理输入|画面|渲5ms|空|渲5ms|完成|画面|
              ↑       ↑    ↑
           浏览器  浏览器  用户输入插队
           可以画  可以画  立即响应
```

**类比**：你在写 200 页报告。没有 Fiber = 关门写完再出来。有 Fiber = 每写 5 页开门看一眼，有急事先处理。

## 四、三者配合的完整流程

以搜索框输入为例：

```
用户快速输入：王 → 王五 → 王五六

第一层：防抖（减少触发次数）
├─ "王"    → 启动 300ms 定时器
├─ "王五"  → 取消上一个，重新 300ms
├─ "王五六" → 取消上一个，重新 300ms
└─ 300ms 到 → 触发 1 次 setFilterText("王五六")
                    │
第二层：React 开始渲染（Fiber 切片）
├─ 小块1：过滤数据 + 处理前 50 个 Fiber 节点（5ms）
│   └─ shouldYield() → 让出
│       └─ 浏览器：画面刷新，检查有没有新输入
├─ 小块2：处理第 51-100 个节点（5ms）
│   └─ shouldYield() → 让出
│       └─ ⚠️ 用户又输入了"七"！
│           └─ startTransition 标记的更新被丢弃
│           └─ 重新从"王五六七"开始
└─ ...最终完成渲染，commit 到 DOM

第三层：滚动时 rAF 节流（减少渲染频率）
├─ scroll 事件 1  → pendingScrollTop = 100
├─ scroll 事件 2  → pendingScrollTop = 120（覆盖，不触发渲染）
├─ scroll 事件 3  → pendingScrollTop = 150（覆盖，不触发渲染）
└─ rAF 回调       → setScrollTop(150)，只渲染 1 次
```
