# 商品搜索页 — 防抖节流实战

> 面试导向项目，手写 useDebounce / useThrottle 自定义 Hook，React 19 + JSX，不依赖第三方库。

## 口诀

**要结果用防抖，要过程用节流**

---

## 三大核心场景

### 场景一：搜索联想（防抖 500ms）

| 项目 | 说明 |
|------|------|
| 触发事件 | input（用户输入） |
| 策略 | 防抖（debounce） |
| 延迟 | 500ms |
| 判断依据 | 只需要最终输入结果，中间过程无意义 |

行为：用户停止输入 500ms 后才发起搜索请求，避免每敲一个字符都请求后端。输入框下方展示联想下拉列表。

### 场景二：滚动加载 + 商品曝光埋点（节流 300ms）

| 项目 | 说明 |
|------|------|
| 触发事件 | scroll（列表滚动） |
| 策略 | 节流（throttle） |
| 延迟 | 300ms |
| 判断依据 | 滚动过程中需持续响应，但不需要每次 scroll 事件都执行 |

行为（两件事合并在一个节流回调里）：

1. **触底检测**：判断 `scrollHeight - scrollTop - clientHeight < 100`，触底则加载下一页商品
2. **商品曝光检测**（模拟真实业务埋点）：
   - 遍历当前所有商品卡片 DOM，用 `getBoundingClientRect()` 判断是否在滚动容器可视区内
   - 首次进入可视区的商品标记为"已曝光"，记录到日志面板
   - 已曝光的商品不重复上报

**为什么加曝光埋点？**
- 真实电商场景标配：运营需要知道"用户看到了哪些商品"来计算曝光→点击转化率
- 技术价值：每次执行都有 DOM 遍历 + getBoundingClientRect 计算，让节流的性能优化效果可感知
- 面试加分：展示业务思维，不只是写 demo

**模拟重计算（heavyCompute）— 让节流效果肉眼可见**：

单纯的 `getBoundingClientRect` 执行太快（<1ms），节流开/关体感差异不大。为了让面试演示时效果立竿见影，在每次滚动回调里加入同步 CPU 密集计算：

- `heavyCompute()`：同步循环 10 万次数学运算（Math.sqrt + Math.sin），模拟真实业务中复杂 DOM 计算的开销，单次约 5-10ms
- 节流关闭时：每次 scroll 事件都执行 heavyCompute → 1 秒内触发 30-60 次 × 5ms = 累积阻塞主线程 → 页面卡顿掉帧
- 节流开启时：300ms 才执行一次 heavyCompute → 1 秒最多 3-4 次 × 5ms = 主线程大部分时间空闲 → 滚动流畅
- 面试话术：「节流不是让计算变快，而是让计算变少」

**统计条**（日志面板顶部）：
- `原始触发: N 次 | 实际执行: M 次 | 节省: X% | 单次耗时: Yms`
- 日志每条也显示执行耗时，方便对比

**节流 vs 无节流对比模式**：
- 开关按钮切换节流/无节流
- 关闭节流时：每次 scroll 事件都执行 heavyCompute + 曝光检测 + 触底判断 → 卡顿
- 开启节流时：300ms 执行一次 → 流畅

### 场景三：窗口 resize 重算布局（防抖 300ms）

| 项目 | 说明 |
|------|------|
| 触发事件 | resize（窗口大小变化） |
| 策略 | 防抖（debounce） |
| 延迟 | 300ms |
| 判断依据 | 只需要最终窗口尺寸，中间过程无意义 |

行为：窗口大小变化停止 300ms 后重算商品列表列数（1-4 列自适应）。

## 自定义 Hook 技术要点

### useDebounce

- 用 `useRef` 存定时器 ID，组件重渲染不丢失
- 用 `useRef` 存最新回调，解决闭包陷阱（避免捕获旧 state/props）
- 支持 `cancel` 方法（面试加分项）
- 组件卸载时自动清理定时器

### useThrottle

- 时间戳 + 尾调用结合版，兼顾 leading（首次立即执行）和 trailing（最后一次保证执行）
- 同样用 `useRef` 存回调避免闭包陷阱
- 支持 `cancel` 方法
